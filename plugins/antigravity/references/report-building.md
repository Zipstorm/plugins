# Build a report

A report is a title, an optional baseline search, one markdown body and the
modules the body places. A module is a card SeekOut measures from the inputs
you give it: a talent map, a market's makeup, requirement trade-offs, a
company's talent flow, a company landscape, internal talent, Outreach counts.
Written modules are an HTML block for a custom table or chart (inline styles
only, no scripts or links), the role's screening rubric and the next steps. A
module shows its data alone. What it means is yours to write in the body
(headings, paragraphs, lists, tables), which places each module where it
belongs. Everyone who can open the report sees each version as it is saved.

Every step is a SeekOut action.

1. **Create** it in SeekOut, in the role's workspace with a title that says what it is
   about (the role and the market), never its kind or the workspace's name, its
   baseline search and its measured modules. The baseline is the search you
   already hold (from this conversation, the pane or the workspace's searches);
   search the role once, as asked, only when you hold none. Once a plan or report
   was asked for, a request or job description that names the role, the market
   and its requirements is enough: create it and measure without asking. Ask only for what no module can be
   measured without. Give each module a key you choose and its inputs. Every module shares the report's baseline, so they
   agree on the baseline count; a module extends it and never redefines it. A
   talent map, a market overview and requirement trade-offs are variants of the
   baseline: they name only places or changes from it, and SeekOut derives,
   saves and measures each variant, so the role is searched once, as the
   baseline, never once per market or requirement. A variant needs the
   baseline; at most 24 new variants go in one change. Two modules of one kind must differ (a
   company flow per company, never the same company twice). SeekOut measures
   them and answers each module's facts; never write a number into a module,
   and never automatically repeat an uncertain paid measurement.
2. **Widen** it from what the modules measured. Each answer carries every module's
   facts and the modules those facts suggest, each ready to send back: a profile of
   a market the map counted, where a leading employer hires from, a measurement the
   report lacks. Add them, change a module's inputs in place (more places, another
   requirement) or drop one, in one change each time, as many times as the request
   needs. The client needs to know nothing of the role beforehand: the facts are
   the context. A requested market that comes back unmeasured is unfinished, never
   zero: correct the input using returned place choices and retry only when the
   result permits it. If it remains unavailable, state the unresolved scope;
   never claim the requested comparison is complete or spend an exhausted
   question budget asking to omit it. An uncertain paid outcome is not an
   invitation to retry. Read back state before repeating an uncertain write.
3. **Write** the body once the scope holds, from the facts: add the next steps (and the rubric, where
   one is written) and set the body, written from those facts: what the
   modules mean for the role, what you recommend and why. The body places every
   module exactly once, on a line of its own, as `![Its title](seekout:<key>)`,
   with the next steps at its end. Link every figure to its report ref, as
   [268 people](#Q1).
4. **Read** the saved body and relevant module fact pages before handoff, before
   building on a saved report, and after an uncertain write. Verify counts,
   populations, citations, gaps and single placement; fix mismatches yourself.
   Repair local call syntax/schema errors and continue; saving setup records is
   not completing a requested report.

## Choose and write

For a role plan or broad role-market report, use this concise recipe:

- A decision headline and one short sentence of distinctive sourced evidence.
- The native visual that best proves it, then up to three short
  evidence-to-action bullets.
- A second visual only when it changes the decision, then native next steps.

Target 140–200 authored words excluding native labels and source metadata, with
at most two short sentences per paragraph. Do not repeat chart totals, describe
tool mechanics, or force a surprising finding. Keeping the brief and reviewing
the baseline is a useful recommendation. Explore as needed, but retain usually
two measured visuals, never more than three unless the recruiter requests more
scope. Remove unused exploratory modules and their embeds; every retained
module appears once. A narrow question can need only one visual.

Use native visuals first. Create custom HTML/SVG only for an essential visual
relationship the native modules cannot express; never decorative text cards,
ordinary markdown-equivalent tables, fake controls or invented scores. Use the
current written-module schema and its rendering restrictions.

Keep one as-written role baseline with required skill families ANDed and
accepted alternatives ORed. Never add an unstated filter. Measure hypothetical
changes independently while keeping fixed requirements and the agreed rubric.
Alternate office locations do not establish commute or relocation willingness.
Inspect relevant title, employer, skill and seniority facts to find differences
beyond pool size. Use each fact's scope and denominator; do not call the largest
employer bucket the whole market's concentration. For non-role questions, use
the scope the chosen module needs instead of inventing a role baseline.

Let the page's source metadata carry dates and technical details. Preserve only
decision-relevant limitations in the prose; if writing a source date, label UTC
or convert it correctly. The next action recommends rather than executes work
not already requested. A hypothetical variant may open for inspection, but must
not be screened against an incompatible unchanged rubric.

Once a report has a body, a module added later waits unplaced until the next
body places it, and a removed module's embed leaves the body first. For a targeted revision, change only the
requested modules and the body text that cites them. Changing a module's
inputs or the baseline measures it again (a new baseline re-derives every
variant): rewrite the body text that cites it.
Leave evidence gaps explicit.

When opening a report, use the workspace and report IDs returned by SeekOut;
never invent a workspace ID. Open it once: later versions reach whoever has it
open. The page supplies its title, modules, sources and versions; the body adds
meaning rather than repetition. Give a short chat handoff.

Every figure needs a source, scope, unit and date. Preserve synthetic and stale
labels. Missing is not zero. Profile counts measure indexed matches, not
availability, demand or pay. Compare equivalent populations; never sum
overlapping groups or invent benchmarks. Keep facts separate from interpretation
and explanations focused on hiring decisions. Shared [evidence](evidence.md)
rules govern privacy, identifying groups and sensitive claims. Read the relevant
[connector note](connectors/README.md) only when using that source.
